# The CSP contract

## The actual problem

`style-src-attr 'none'` blocks the HTML `style` *attribute*. It does not
block a script from doing `el.style.transform = ...` or
`el.style.setProperty(...)` at runtime — those aren't attribute writes,
they're direct CSSOM property assignments, and most browsers don't gate
them behind `style-src-attr` at all. A slider that positions slides via
`element.style.transform = 'translateX(...)'` — the most common
implementation technique — can pass a CSP audit that only checks for the
`style=` attribute in markup while still being fundamentally built on
inline styling that a stricter audit, or a future policy tightening, would
flag.

This package's actual contract, enforced by construction and by the test
suite in `tests/e2e/csp.spec.ts`, is stricter than what CSP directives
alone require:

- No `style` attribute, ever, including transient ones during drag/resize/
  animation/teardown.
- No `element.style` writes, `style.setProperty`, `style.cssText`,
  `setAttribute('style', ...)`, or framework style props, anywhere in the
  runtime code path.
- No inline `onclick`/`on*` attributes; all event binding is
  `addEventListener`, removed on `destroy()`.
- No injected `<style>` elements, no runtime CSS text generation, no
  stylesheet rule insertion (`CSSStyleSheet.insertRule`), no constructed/
  adopted stylesheets used as a style-injection workaround.
- No `eval`, `new Function`, string-based timer arguments, or
  `javascript:` URLs.
- No dependency on `'unsafe-inline'`, `'unsafe-eval'`, `'unsafe-hashes'`,
  nonces, or hashes for ordinary operation.

## How positioning works without any of that

Slides live in a native scrollable container
(`overflow-x: auto` + `scroll-snap-type`, defined entirely in
`css/csp-safe-slider.css`). Navigation is `track.scrollTo({ left, behavior
})` or direct `track.scrollLeft =` assignment — both are **DOM element
properties/methods**, not styling, and are unaffected by any CSP directive.
Slide sizing (`flex-basis`, gaps, colors) is 100% your external CSS via
custom properties; JS only ever *reads* layout (`offsetLeft`,
`getBoundingClientRect`) to compute scroll targets, never writes it.

State that needs to reach CSS (which slide is active, current axis, drag
state) is expressed as class toggles and `data-*`/`aria-*` attribute
writes — both are plain DOM attribute operations, not styling, and their
*visual effect* is entirely defined in the static external stylesheet you
control, not generated by JS.

## How seamless loop stays CSP-safe

`mode: 'loop'` clones the full slide set once before and once after
itself (`[clones][real slides][clones]`) so any viewport can wrap
correctly. When a scroll settles inside a clone region, the engine jumps
`scrollLeft`/`scrollTop` directly (a property write, not a style write) to
the equivalent position in the real block — instant, no animation, and
imperceptible because the clone is visually identical to what it stands in
for. The jump distance is *measured* from actual `offsetLeft` layout, not
assumed from a fixed slide width, so this also works for variable-width
slides. See `src/core/loop.ts`.

Clones are neutralized so they can't be mistaken for real, interactive
content: `aria-hidden="true"`, the `inert` IDL property (a DOM property,
not a style), stripped `id` attributes (to avoid duplicate IDs), and
`tabindex="-1"` on any focusable descendant.

## Why touch drag is left to the browser

Mouse "click and drag to scroll" isn't a native browser behavior for a
scrollable `<div>`, so this package implements it in JS (`src/core/drag.ts`)
using the same `scrollLeft` property-write technique. Touch swipe, on the
other hand, **is** native browser behavior for any `overflow: auto`
container — reimplementing it in JS would add risk (fighting the browser's
own momentum/rubber-banding) without any CSP benefit, so touch input is
intentionally left to the platform (`touch-action` is set in CSS to scope
it to the right axis).

## The two policies this is tested against

```http
# Primary — the directive-by-directive baseline this package targets
Content-Security-Policy: default-src 'none'; script-src 'self'; script-src-attr 'none'; style-src 'self'; style-src-elem 'self'; style-src-attr 'none'; img-src 'self'; media-src 'self'; font-src 'self'; connect-src 'none'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'none'

# Fallback — proves the package doesn't rely on the *-attr/*-elem directives existing
Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; media-src 'self'; font-src 'self'; connect-src 'none'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'none'
```

Both are served with a real enforcing header (not report-only) by
`tests/e2e/fixtures/server.mjs`, exercised by `tests/e2e/csp.spec.ts` across
Chromium, Firefox, and WebKit. Results are in
[VALIDATION_REPORT.md](VALIDATION_REPORT.md).

## Negative control

A policy that silently isn't enforcing (misconfigured header, report-only
mode, a dev server injecting its own styles) would make "zero violations"
meaningless. `tests/e2e/fixtures/negative-control.html` contains an
*intentional* forbidden inline `style` attribute and an intentional
`onclick` handler; the test suite asserts both are actually blocked
(computed style doesn't apply, handler doesn't run) and reported via
`securitypolicyviolation`, proving the policy is live before trusting the
zero-violation result on the real fixture.

## What this does *not* cover

The CSP contract is scoped to code this package generates. It does not and
cannot make the following compliant on your behalf:

- **Your own host page code** — if your app writes `el.style.color = ...`
  elsewhere, that's outside this package's control.
- **Custom render callbacks** — if you pass slide content or a custom
  control renderer, whatever DOM/attributes *you* construct there are your
  responsibility; this package never accepts raw HTML strings for
  package-generated UI (no `innerHTML`) and expects the same discipline
  from consumer-supplied content.
- **Media and third-party embeds** — an `<iframe>` or video source you
  embed inside a slide has its own CSP obligations (`frame-src`,
  `media-src`, etc.) that this package doesn't police.
- **A policy that blocks the package's own required files** — the contract
  assumes your `script-src`/`style-src` permit the package's JS and CSS to
  load at all (typically `'self'` if self-hosted, as in the fixtures
  above). A policy that blocks its own required assets isn't a
  compatibility gap in this package.
